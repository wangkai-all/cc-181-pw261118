# 本地样例：合并 / 删除交错执行，与中途失败恢复

这份文档是 `scripts/scenario_interleave.py` 的可读版本。脚本可以在本地重建整条
路径并断言全部不变量：

```bash
.venv/bin/python scripts/scenario_interleave.py --root /tmp/posdel-scenario --force
```

它不需要服务、不需要浏览器；所有状态都写在 `--root` 指定的目录里，结束后可以
用工作台打开：

```bash
.venv/bin/python scripts/run_server.py --root /tmp/posdel-scenario
```

样例库使用 4 列 schema（`id int64 / city string / temp_c float64 / ok bool`），
24 行，初始切成 3 个 8 行的 Parquet 文件。

下面贴的是实际运行输出。时间戳、文件 ID、删除集 ID（内容哈希包含创建时间）
每次运行都会不同；行数、位置和处置方式是可复现的。

---

## 1. 初始化：24 行 → 3 个不可变文件

```
=== 1. 初始化：24 行写入 3 个不可变 Parquet 文件 ===
快照 v000001  {'raw_rows': 24, 'deleted_rows': 0, 'visible_rows': 24,
               'file_count': 3, 'delete_set_count': 0}
```

`posdel.json` 创建，`head = v000001`。三个文件各 8 行，行位置 `0..7`。

---

## 2. 条件删除：写入独立行位置集合

```
=== 2. 条件删除：temp_c > 20 的行 → 独立位置集合 ===
快照 v000002  {'raw_rows': 24, 'deleted_rows': 4, 'visible_rows': 20,
               'file_count': 3, 'delete_set_count': 3}
```

`temp_c > 20` 命中 4 行，分布在 3 个文件上，因此产生 **3 个删除集**
（每文件最多一个）。Parquet 文件**一个字节都没改**；只是清单里多了引用。

这时 head 是 `v000002`，原始行仍 24 行，可见 20 行。

---

## 3. 准备合并任务（基线 = 当前 head）

```
=== 3. 准备合并任务（基线 = 当前 head，输入 3 个文件） ===
任务 j_a7116d4dcf  基线 v000002  输入 3 文件
映射偏移（file → merged 起点）：{'f_5e1ff2a2f8305bbf': 0,
                                 'f_e44292289c0b88fa': 8,
                                 'f_117c93dffc0fa815': 12}
```

准备阶段做了两件事：

* 在共享锁下抓取基线 `v000002` 的清单、三个输入文件、以及每个文件的删除位置；
* **释放锁**，按基线的可见性把 20 行写进
  `staging/j_a7116d4dcf/merged.parquet`，并记录 `mapping` 与
  `mapping_offsets`。

此时 head 仍是 `v000002`；合并结果不可查询，任务状态 `prepared`。

锁在写文件之前释放，是**故意**的：真实系统里重写可能很慢，不能一直堵住写者。
这也正是下一幕交错发生的地方。

---

## 4. 合并尚未提交，另一个写入者又删除了一批行

```
=== 4. 合并尚未提交时，另一个写入者又删除了一批行 ===
并发快照 v000003  {'raw_rows': 24, 'deleted_rows': 8, 'visible_rows': 16,
                   'file_count': 3, 'delete_set_count': 3}
```

第二个写入者用 `temp_c < 12` 删除，得到 `v000003`，head 前进。合并任务
`j_a7116d4dcf` 的基线 `v000002` 已经**不是** head 了，它准备好的输出基于旧文件，
记录的位置映射也只对旧文件有意义。

关键点：**不能**把 `v000003` 新增的删除位置直接写到合并后的新文件上 —— 行在
新文件里的位置已经全变了。直接套用会删错行。

---

## 5. 提交合并：检测冲突 → 位置映射吸收

```
=== 5. 提交合并：基线已变化 → 检测冲突并通过位置映射吸收新删除集 ===
处置方式: absorbed
  删除集 d_673c6f4ca8cd16abc103 自文件 f_5e1ff2a2f8305bbf:
      旧位置 [0, 1] → 新位置 [0, 1]
  删除集 d_dc90e39647789a527687 自文件 f_e44292289c0b88fa:
      旧位置 [7] → 新位置 [11]
  删除集 d_5ab774216a0c09a6a100 自文件 f_117c93dffc0fa815:
      旧位置 [0] → 新位置 [12]
合并后快照 v000004  {'raw_rows': 20, 'deleted_rows': 4, 'visible_rows': 16,
                     'file_count': 1, 'delete_set_count': 1}
```

提交在独占锁下比较基线与 head：

* 输入文件都还在（没有人替换它们），只是新增了删除集 → `absorbed`；
* 三个新删除集的位置在新文件中的落点用
  `mapping_offsets + index_in_mapping` 换算：
  `f_B` 旧 7 → `8 + 3 = 11`，`f_C` 旧 0 → `12 + 0 = 12`；
* 合并时基线已有的 4 个删除位置被**物理丢弃**（这 4 行不在输出里），所以新
  文件是 20 行而不是 24 行；
* 吸收后的删除集以新的内容哈希写入 `deletes/`，`derived_from` 指向上游删除集，
  页面把这类标记为 `合并重映射`。

合并后的清单同时记录处置方式与每次尝试：

```json
"disposition": "absorbed",
"conflict":   {"mode": "absorb", "added": [ … remap: {"7": 11} … ]},
"absorbed_delete_sets": [
  {"from_delete_set": "d_dc90…", "from_file": "f_e442…",
   "old_positions": [7], "remap": {"7": 11}, "new_positions": [11], …}
]
```

这件事在页面上也能看到：合并提交后 toast 显示
`合并已提交 v000004 · 吸收 1 个并发删除集`，任务详情里写着 `absorbed — 检测到
基线之后的删除，已通过位置映射重映射`，数据文件卡片上该删除集带黄色
`合并重映射` 标签。

---

## 6. 校验：删除语义跨合并仍成立

```
=== 6. 校验：删除语义跨合并仍成立 ===
可见行一致：16 行
合并后原始行 = 20，删除位置 = 4
```

脚本比较合并前后的可见 `id` 集合，断言完全相等。原始行从 24 降到 20（基线
删除被物理丢弃），剩余 4 个删除位置对应并发删除，新快照 `deleted_rows=4`、
`visible_rows=16`。

> 若处置是 `redone`（输入文件被另一个合并替换），脚本同样保证可见集合不变。
> 单元测试 `test_conflict_with_intervening_merge_triggers_redo` 覆盖了这条路径：
> 两个任务同时准备，先提交一个，再提交另一个 —— 旧映射失效，任务按当前 head
> 重新规划，不会复活旧文件、也不会重复行。

---

## 7. 中途失败：目录切换前注入崩溃

```
=== 7. 准备第二个合并，并在“目录切换前”注入崩溃 ===
注入崩溃：posdel.json 尚未切换
崩溃后 head 仍是 v000004（合并不可见，旧版本继续可查）
```

脚本用 `commit_merge(..., fault_inject=...)` 在 `before_catalog_swap` 处抛错。
这模拟进程在「合并文件已发布、删除集已写、快照清单已写，但 **`posdel.json` 还没
换**」的时刻被杀掉。

此时：

* 磁盘上多了一个 `data/f_<uid>.parquet`（合并输出）和可能的删除集文件 —— 它们
  不被目录引用，因此**不可达**；
* `head` 仍是 `v000004`，所有查询继续读旧数据；
* 任务记录停在 `committing`。

崩溃点可以在页面上选择（「提交前注入崩溃（目录尚未切换）」等），方便观察每个
窗口。

---

## 8. 重启进程并执行恢复

```
=== 8. 重启进程并执行恢复：重放提交 ===
恢复动作: ['recommit_job', 'remove_staging', 'remove_staging']
恢复后 head v000005  {'delete_set_count': 1, 'deleted_rows': 0,
                     'file_count': 1, 'raw_rows': 16, 'visible_rows': 16}
```

`recover()` 扫描活动任务：

* `committing` 且目录中没有引用它的快照 → 输出仍在且 sha256 匹配 →
  **重新提交**（复用已发布文件，不重复写）；
* 提交成功后，附带清理不再被活动任务使用的 `staging/` 目录（两条
  `remove_staging` 分别对应第一次已提交合并和本次崩溃任务留下的暂存目录）——
  恢复对提交本身只做一次 `recommit_job`；
* 结果：新快照 `v000005`，head 前进，没有任何重复输出。

恢复后脚本再次断言可见集合与合并前一致，并且 `verify(full=true)` 通过。

另一种窗口是 `after_catalog_swap`：崩溃时新快照**已经可见**，只是任务文件没
更新。`recover()` 会发现快照的 `operation.job_id`，只把任务标为 `committed`，
**不会**再写一个快照。这条路径由
`tests/test_maintenance.py::test_recovery_after_catalog_swap_marks_job_only`
覆盖；再跑一次 `recover()` 没有任何动作（幂等）。

---

## 9. 安全回收范围

```
=== 9. 安全回收预览 + 执行（只保留最近 2 个快照） ===
预览：10 个不可达文件，12210 字节，将过期 ['v000001', 'v000002', 'v000003']
已回收 10 个文件，释放 12210 字节
```

预览是**非破坏性**的：只计算「如果保留最近 2 个快照，哪些文件/删除集/清单将
不再可达、哪些旧快照将过期」，不删除任何东西。确认后再执行
（API 要求 `confirm=true`）。

执行后 `v000001..v000003` 被标记为过期（仍列在历史中，但查询返回 409），
它们的清单与数据文件被删除；head `v000005` 不受影响，可见行集合不变。

页面上「维护」卡片就是这个流程：输入保留快照数 → 预览可回收范围 →
「执行回收」按钮在预览后启用。

## 10. 在工作台上重放同样的交错流程

启动演示服务：

```bash
.venv/bin/python scripts/run_server.py --demo      # http://127.0.0.1:8765
```

1. 点击「初始化示例湖表」（或页面提示的重置按钮）。
2. 在「条件构建 / 删除」加条件 `temp_c > 22`，先「预览影响」，再「执行删除」。
3. 在「合并」卡片点「① 准备合并任务」——此时任务 `PREPARED`，head 不变。
4. **先不要提交**。回到删除卡片，再加条件 `id < 4` 并执行删除。
   这是「合并期间另一个写入者」；head 前进，合并基线落后。
5. 回到合并卡片点「② 提交」：任务详情显示
   `absorbed — 检测到基线之后的删除，已通过位置映射重映射`，
   toast 显示吸收了并发删除集，并跳到新版本。
6. 左侧「数据文件」里，新合并文件上的删除集带 `合并重映射` 标签，
   「删除来源」卡片显示 `来源标记：合并重映射（上游删除集 …）`。
7. 浏览器切到旧版本（如 `v000002`）：查询结果按该版本同时应用**当时**的数据
   文件与删除记录。
8. 再准备一个合并，提交时在「正常提交」下拉里选
   「提交前注入崩溃（目录尚未切换）」→ 页面提示崩溃已注入、head 未前进。
   点左侧「崩溃恢复」，任务被重放，head 前进。
9. 「维护」里把保留快照数设为 1，先「预览可回收范围」再「执行回收」；
   过期版本仍列在左侧但点击查询会提示已过期。
